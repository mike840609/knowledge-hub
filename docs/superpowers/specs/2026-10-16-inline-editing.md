# Direct document editing — first increment

Writable, active Hub documents open an inline Milkdown editor on the canonical document URL. Opening a document neither focuses the editor nor writes a revision. Historical queries, archived sources/documents/workspaces, external sources and viewers remain read-only. Legacy `/edit` bookmarks redirect to the canonical document.

Use the reader frame, share actions, inspector, outline and backlinks. The title still follows metadata → opening H1 → typed title. The native borderless title field is an intentional design-contract §3 exception, matching DocumentComposer's document surface rather than a form control. The Markdown source is the shared code surface decided 2026-11-18 (`2026-11-18-editor-source-and-title-design.md`), not a borderless reading field.

Save changed snapshots after one second of inactivity, with a five-second maximum wait during continuous input (amended 2026-11-16 from three and fifteen seconds; see "Leaving and failures"). Composition and authorization pauses take priority; an in-flight request always finishes before the next starts. Serialize PATCH requests against the last acknowledged revision; typing remains enabled during requests. Keep recovery text locally on each change; synchronize account recovery on failure or leaving, and deduplicate empty recovery clears after successful saves. Preserve recovery text independently of document persistence, stop on conflicts and other refusals, and require an explicit decision before publishing a recovered draft written over an older revision (amended 2026-11-16, "Leaving and failures" below). Discarding recovery requires confirmation. A plain visit must not publish normalized Markdown, nor a recovered draft written over an older revision.

Comment creation and passage locations wait while the editor has unsaved content; existing discussions remain accessible. Update the title, timestamp and revision list locally after saves. Coalesce server-owned metadata and navigation refreshes into one thirty-second window, or refresh earlier when Details is opened, without replacing the editor. Do not rewrite immutable revisions or introduce collaborative merge semantics in this increment (a conflict whose sides changed different lines is merged since 2026-11-16, "Leaving and failures"; there is still no live co-editing).

Verification covers no-write visits, save/reload, slow network typing, conflicts, recovery, readonly history, source fallback, and composition. Existing manual-save E2E scenarios need migration to the new interaction contract. New-document creation used its explicit Create workflow until 2026-11-16; a new note is now made at once ("Leaving and failures").

Normal saves show no status. A request still pending after one second shows Saving; its success is confirmed for two seconds. Failures and recovery remain visible in a stable toolbar slot.

## Leaving and failures (amended 2026-11-16)

Notion keeps what was typed without asking; this section brings leaving and failed saves in line with it. It replaces the earlier rules that a recovered draft always waits for Resume saving and that every failed save waits for Retry save.

- **Leaving sends what is unsaved.** When the editor goes through navigation inside the app, or the page is hidden or closed (`visibilitychange` to hidden, `pagehide`), the unsaved snapshot is sent at once as a `fetch` with `keepalive`, so the request outlives the page. If a write is already in flight, the rest follows once it is acknowledged; on in-app navigation it is still sent after the editor is gone. A snapshot over 60,000 bytes as JSON (line breaks escaped) is sent as an ordinary request, because the browser refuses a larger `keepalive` body. The recovery copy is kept until the save is acknowledged.
- **The browser's leave prompt** appears only when unsaved text cannot go with the page: the snapshot is over the size limit, saving is paused (composition, stale recovery, no write access), the last save failed, or a write is still in flight.
- **A recovered draft written over the current revision** is the writer's own unsaved text, from this tab or, in a personal workspace, from the account copy another device left. It opens with saving resumed, with no notice and no Resume saving step. Version history keeps what it replaces. A draft written over an older revision still waits: it is shown, paused, with Download and Discard, because saving it would overwrite what was saved since.
- **A transient failure is retried automatically.** That means no response at all, or a 5xx, 408 or 429 status. The retry comes 2 s after the failure, then 4 s, 8 s and so on, never more than 30 s apart, always with the latest text. It is retried at once when the browser reports it is online again or the page becomes visible. While retrying, the failure stays visible with "Trying again automatically." and Retry save remains. Conflicts and other refusals (4xx) are not retried; they stop as before.
- **A save of what is already current is not a conflict.** A plain autosave whose title, Markdown and metadata equal the current revision answers unchanged with that revision, whatever revision it named as its base. A reload races the request sent on leave: the new page may resume the same draft against the revision that request just replaced. Named versions and restores still require the current base (`create-revision.ts`).

- **Saving comes sooner.** The delays are one second after the last change and five seconds during continuous typing, down from three and fifteen. Editing is single-writer, so a shorter delay adds no merge risk; it shortens what a crash (where nothing is sent on leave) can lose and how stale other devices are. Version history does not grow with it: autosaves replace the working revision and checkpoints are taken by time (`revision-history.ts`). The cost is one full-document write about every five seconds of typing, not a per-keystroke stream; saving changes as operations rather than snapshots would be a different design.
- **An idle tab catches up.** A tab with nothing unsaved shows the newest revision when another tab of the same browser saves the document (announced over a `BroadcastChannel`) and whenever the page becomes visible again (a save from another device), by refreshing the server snapshot that the editor already adopts only over an idle baseline. So the next keystroke starts from what was saved elsewhere instead of meeting a conflict. A tab with unsaved text is never replaced.
- **An untitled page saves.** When metadata, an opening H1 and the typed title are all empty, the page is saved with the title "Untitled" instead of pausing with "Add a title"; the next title typed replaces it. The stored title is never empty, so lists, search and links need nothing new.

- **A conflict on different lines merges.** When a save is refused as a conflict, the editor reads the current revision (`/peek?brief`) and merges by lines, three ways: the last acknowledged text is the base, the editor's text is mine, the current revision is theirs (`src/lib/merge-text.ts`, the rule `git merge-file` uses). If the two sides changed different lines, not neighbouring ones, the merged text is shown in the editor and saved against the current revision with no notice. A title merges the same way: whichever side changed it wins, and both changing it differently is a conflict. Changes to the same or neighbouring lines, or to the title on both sides, stop as before with "Someone updated this document" and Download. The merge replaces the editor's document, so the caret may move. A stale recovered draft is not merged: its base text is not in the page.
- **A new note exists at once.** `/knowledge/new` (New note, `C` on Home, Create document, New document here, a broken link's create) creates the document "Untitled" — or with the title a broken link gave it — in the asked folder, and replaces itself in history with the document in the inline editor, the title focused and "Untitled" selected. From there it is an ordinary document: autosave, leaving, recovery. A refusal (no write access, a folder gone) is shown in words on that page. A note left empty stays, as an empty Notion page does; archive it like any other. The form with a Create button remains at `/knowledge/new?compose`: for uploading a `.md` file, and for a new-note draft written there before (Home's Drafts link to it). The page is server-rendered only for writers, so a prefetch creates nothing; the create runs in the browser, once per address within five seconds (a double click or a remount opens the same note).

Not changed: composition pauses.

## Typing-first keyboard behavior

Page and folder commands are invoked through explicit controls or the command palette. Remove global and row F (favorite), M (move), C (create), D (discussions), and R (rename) bindings and their visual/accessibility hints. Plain slash no longer opens global search; the editor retains its own slash behavior. Cmd/Ctrl+K opens the palette only when the event has not already been handled by the editor, and never during IME composition. Row arrows and J/K navigation remain local to the tree. Discussion buttons remain available on owner and shared pages.

One exception, added 2026-10-19: personal Home answers `C` with a new note. Home has no editor, and the listener is mounted with Home only, so no page that holds the inline editor ever sees it (`2026-10-19-home-continue-design.md`, "New note key"; `tests/e2e/keyboard-shortcuts.spec.ts` checks both sides).

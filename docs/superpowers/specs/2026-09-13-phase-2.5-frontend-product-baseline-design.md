# Phase 2.5 — Frontend Product Baseline Design

**Status:** Approved for implementation planning  
**Scope:** Frontend architecture and UX stabilization  
**Product:** Knowledge Hub  
**Depends on:** Phase 0–2 domain and backend contracts  
**Next phase:** Phase 3 — Workspace Governance

## 1. Summary

Phase 0–2 established the Knowledge Hub domain model, Workspace-scoped access, Knowledge Sources, tree/document browsing, immutable revisions, archive lifecycle, and folder ingestion through Preview → Confirm → Apply.

The current frontend validates these capabilities, but its structure is still closer to a verification interface than a production Knowledge Hub.

Phase 2.5 converts that frontend into the stable product shell that Phase 3–6 can build upon. It does not add new domain capabilities.

> Establish the final frontend information architecture, navigation model, knowledge browsing experience, source-management workflow, responsive behavior, and visual language before additional product capabilities are introduced.

The product is not yet live, so no backward-compatibility or frontend migration layer is required. Phase 2.5 may directly replace the current frontend architecture.

## 2. Goals

Phase 2.5 MUST:

1. Establish a persistent Workspace-scoped application shell.
2. Separate knowledge consumption from source management.
3. Make document browsing a continuous Tree → Document workflow.
4. Render Markdown as human-readable content rather than raw text.
5. Provide document metadata and revision history without cluttering the reading surface.
6. Move folder import/update into a dedicated Sources management workflow.
7. Make Import Preview a proper safety/review surface.
8. Provide deterministic navigation behavior.
9. Establish responsive behavior for desktop, laptop, and narrow screens.
10. Establish consistent loading, empty, and error states.
11. Adopt a stable Linear/GitHub-inspired visual language.
12. Preserve Phase 0–2 backend/domain contracts.

## 3. Non-goals

Phase 2.5 MUST NOT introduce:

- Global knowledge search
- Semantic or hybrid search
- Human document authoring
- New document creation
- Workspace administration
- Workspace member management
- Roles or capability management
- Publishing or tKMS publishing UI
- MCP administration
- Agent Memory UI
- Favorites
- Recent documents
- Dashboard analytics
- Dark mode as a Phase 2.5 deliverable
- Workspace or Source slugs
- Tree lazy-loading APIs
- A new global state-management framework
- Obsidian-specific rendering extensions
- Syntax highlighting
- Internal wiki-link resolution

## 4. Product mental model

The frontend MUST reflect the canonical hierarchy:

```text
Workspace
  ├─ KnowledgeSource
  │    └─ Tree
  │         └─ Document
  │              └─ Revision
  └─ KnowledgeSource
```

A Workspace is the user-facing collaboration and access context.

A Source is the provenance and ownership boundary for knowledge and the logical root of its own tree.

The frontend MUST NOT synthesize all Sources into one artificial Workspace tree.

## 5. Information architecture

Phase 2.5 contains only two primary sections:

```text
Knowledge Hub
├─ Knowledge
└─ Sources
```

There is no Home page and no Settings page in Phase 2.5. Future navigation items are not shown as placeholders.

The authenticated user enters directly into Knowledge within an accessible Workspace.

## 6. Application shell

The persistent shell contains:

```text
┌──────────────────────────────────────────────────────────────┐
│ Knowledge Hub     Workspace ▼                         User   │
├───────────┬──────────────────────────────────────────────────┤
│ Knowledge │                                                  │
│ Sources   │                    Page Content                  │
│           │                                                  │
└───────────┴──────────────────────────────────────────────────┘
```

### 6.1 Topbar

The Topbar contains:

- Product name
- Workspace selector
- Current user identity

The Workspace selector displays only the Workspace name. It MUST NOT display `org_code`, future roles, ownership metadata, or permissions.

Workspace selection is navigation state only and MUST NOT be treated as authorization evidence.

### 6.2 Primary navigation

The Phase 2.5 Primary Nav contains only:

- Knowledge
- Sources

Navigation uses icon + text labels and does not collapse into an icon-only rail on desktop.

Recommended width: **150–180px**.

## 7. Routing

Phase 2.5 adopts hierarchical Workspace-scoped routes. Identifiers remain UUIDs; no slug lifecycle is introduced.

### 7.1 Root

`/` resolves:

```text
first accessible Workspace
  → first Source by deterministic name order
    → first readable Document by existing Tree order
```

and navigates directly to the resulting canonical Knowledge route.

### 7.2 Knowledge routes

Canonical document route:

```text
/w/:workspaceId/knowledge/:sourceId/:documentId
```

Source-only route:

```text
/w/:workspaceId/knowledge/:sourceId
```

resolves the first readable Document according to Tree order.

Workspace Knowledge route:

```text
/w/:workspaceId/knowledge
```

resolves the first Source by name, then the first readable Document by Tree order.

### 7.3 Source routes

```text
/w/:workspaceId/sources
/w/:workspaceId/sources/:sourceId
/w/:workspaceId/sources/import
/w/:workspaceId/sources/:sourceId/update
/w/:workspaceId/sources/imports/:snapshotId
```

### 7.4 Existing routes

Existing frontend routes such as:

```text
/knowledge
/knowledge/:documentId
/knowledge/imports/:snapshotId
```

are removed. No redirects or compatibility layer are required.

## 8. Navigation rules

### 8.1 Workspace change

Switching Workspace resets content context:

```text
new Workspace
  → first Source by name
    → first readable Document by Tree order
```

The frontend does not attempt to find similarly named Sources or Documents.

### 8.2 Source change

Selecting another Source opens its first readable Document according to existing Tree order.

### 8.3 Navigation persistence

Phase 2.5 does not persist last Workspace, last Source, last Document, or Inspector state in localStorage/session storage.

The URL is the authoritative navigation state.

## 9. Knowledge Explorer

Knowledge is the high-frequency reading workspace.

Desktop composition:

```text
Primary Nav | Source Tree | Document | optional Inspector
```

The Tree remains visible while switching Documents on desktop. Opening a Document MUST NOT remove Tree context.

## 10. Source sidebar

The Knowledge sidebar contains:

- Source selector
- Source actions (`…`)
- Tree filter
- Knowledge Tree

Recommended fixed width: **~280px**.

The width is not user-resizable in Phase 2.5.

### 10.1 Source selector

Only one Source Tree is mounted at a time.

There is no `All Sources` option.

Sources are ordered deterministically by name. The selector does not include search in Phase 2.5.

### 10.2 Source actions

A `…` menu provides secondary Source actions. For folder-managed Sources it may contain `Update from folder`.

This is only a shortcut into the canonical Sources update flow. Knowledge MUST NOT implement a second synchronization workflow.

## 11. Knowledge Tree

### 11.1 General behavior

The Tree uses the existing Source Tree structure and loads the entire Source Tree through the existing read contract.

Phase 2.5 does not introduce lazy loading or virtualization.

### 11.2 Folder interaction

Clicking a folder row toggles expanded/collapsed state. A folder overview page is not introduced.

### 11.3 Document selection

The selected Document uses a full-row selected state.

Tree expansion state survives Document navigation.

### 11.4 Tree filter

Phase 2.5 includes a local filter over the currently loaded Source Tree.

When filtering:

- matching nodes remain visible
- ancestor folders remain visible
- required ancestors automatically expand

When the filter is cleared, the pre-filter expansion state is restored.

This is not Phase 4 Search.

### 11.5 Archived content

Archived content is hidden by default.

A Tree/Source menu option exposes `Show archived`.

Phase 2.5 does not expose Archive/Restore write actions.

### 11.6 Long names

Long folder/document names use single-line ellipsis plus tooltip/full-value affordance. Horizontal Tree scrolling is avoided.

### 11.7 Keyboard navigation

The Tree supports conventional keyboard behavior:

```text
↑ ↓  move selection/focus
←    collapse or move toward parent
→    expand
Enter open/select
```

All interactive elements require visible focus state.

## 12. Document experience

### 12.1 Layout

Desktop:

```text
Tree | Document | optional Inspector
```

Document content remains fluid, but readable body width is constrained to approximately **760–900px**.

### 12.2 Document header

The Header is compact and sticky for long documents. It contains:

- Breadcrumb
- Document title
- important state such as `Read only` or `Archived`
- absolute updated timestamp
- Details action
- contextual `…` actions

Detailed technical metadata belongs in the Inspector.

### 12.3 Breadcrumb

Breadcrumb hierarchy:

```text
Source / Folder / … / Document
```

Long middle paths collapse to `…`.

### 12.4 Timestamp

Use stable absolute display such as:

```text
Updated Sep 13, 20:10
```

Do not require continuously changing relative timestamps.

## 13. Markdown rendering

Raw Markdown `<pre>` rendering is removed.

Phase 2.5 supports safe CommonMark/GFM-style presentation including:

- headings
- paragraphs
- ordered/unordered lists
- blockquotes
- links
- tables
- task lists
- code blocks
- basic URL-backed images

Raw HTML is not executed.

### 13.1 Code

Code blocks use basic monospace presentation without syntax highlighting or a copy button.

Long code blocks scroll horizontally inside their own container.

### 13.2 Tables

Wide tables scroll horizontally inside the table container rather than forcing page-level horizontal scrolling.

### 13.3 Links

External links open in a new tab and show an external-link indicator.

Phase 2.5 does not resolve relative Markdown paths into Hub Document IDs.

### 13.4 Images

Images with resolvable supported URLs may render. Failed/unavailable images display a graceful placeholder.

A Source asset pipeline is outside Phase 2.5.

### 13.5 Document title

The domain Document title is authoritative for the application header. Markdown H1 remains part of rendered Markdown content.

The renderer should avoid visually awkward duplicate title treatment where practical without inventing new domain rules.

## 14. Document Inspector

The Inspector is closed by default.

It contains two tabs:

- Details
- History

Recommended desktop width: **~320px**.

### 14.1 Details

Details may include:

- Workspace
- Source
- Document status
- current revision
- created/updated information
- Source provenance where available

Technical IDs belong in this surface, not in the article body.

### 14.2 History

History shows revisions chronologically and clearly identifies the current revision.

Viewing a historical revision indicates that it is historical and offers `Back to current`.

## 15. Sources

Sources is the management surface for how knowledge enters the Workspace.

Mental model:

```text
Knowledge = consume knowledge
Sources   = manage where knowledge comes from
```

## 16. Sources List

Route:

```text
/w/:workspaceId/sources
```

The page uses compact rows, not large cards.

Each Source row displays:

- Source name
- compact Source-type badge
- latest import timestamp when relevant
- latest import success/failure state

The whole row enters Source Detail.

Phase 2.5 does not provide Source list search/filter.

## 17. Source Detail

Route:

```text
/w/:workspaceId/sources/:sourceId
```

Source Detail is a single page with:

```text
Header
Overview
Import history
Technical details
```

For folder-managed Sources, `Update from folder` is the primary top-right action.

Technical details are collapsed by default.

## 18. Folder Import

New Source:

```text
Sources → Import folder
```

Update:

```text
Source Detail → Update from folder
```

or the Knowledge Source `…` shortcut.

Both update entry points converge on the same canonical workflow.

## 19. Import Preview

Import Preview is a dedicated full page, not a Modal or Drawer.

Structure:

```text
Import Preview
Target Source
Summary
Warnings / Blockers
Added
Updated
Moved / Renamed
Archived / Restored
Unchanged
----------------------
Cancel          Apply
```

### 19.1 Change grouping

Defaults:

- Added — expanded
- Updated — expanded
- Moved/Renamed — expanded
- Archived/Restored — expanded
- Unchanged — collapsed

### 19.2 Change rows

A normal row displays path, change type, and warning/blocker indicator when relevant.

Moved/Renamed entries additionally display:

```text
old/path → new/path
```

Unnecessary technical metadata is hidden by default.

## 20. Import safety

### 20.1 Warnings

Warnings appear in the page-level Summary and on affected rows. Warnings do not automatically block Apply.

### 20.2 Blockers

Blockers appear prominently, identify affected entries, and disable Apply.

There is no user override/force-apply path.

### 20.3 Stale Preview

A stale Preview disables Apply, explains that Source state changed, and offers `Refresh preview`.

### 20.4 Apply

Apply/Cancel uses a sticky footer.

Normal Apply does not require an extra confirmation dialog.

During Apply, CTA is disabled and processing state is visible.

### 20.5 Success

Successful Apply returns to Source Detail and shows an inline success message with refreshed import status.

### 20.6 Failure

Failed Apply remains on Preview and preserves diff/error context. If the Preview is no longer valid, the user is prompted to refresh/rebuild it.

## 21. Responsive behavior

The application is desktop-first.

### ≥1440px

```text
Primary Nav | Tree | Document | optional Inspector
```

### 1024–1439px

```text
Primary Nav | Tree | Document
```

Inspector becomes a Drawer.

### <1024px

Document becomes a full-page reading surface.

- Primary Navigation becomes a Drawer/menu
- Tree opens via `Browse` Drawer
- Inspector uses a Drawer
- only one overlay Drawer may be open at a time

## 22. Loading states

Loading is scoped to the affected region.

Use Skeleton UI rather than generic spinners or `Loading...` text.

```text
Workspace loading → shell skeleton
Tree loading      → Tree skeleton
Document loading  → Document skeleton
Inspector loading → Inspector skeleton
```

Tree navigation should remain mounted while a Document loads.

## 23. Empty states

Empty states contain a short explanation plus one primary action.

No Sources:

```text
No knowledge sources yet.
[Import folder]
```

Empty Source:

```text
This source does not contain any readable documents.
[Go to Sources]
```

The frontend does not silently switch to another Source.

## 24. Error states

Errors stay scoped to the affected UI region where possible.

Recoverable Tree/Document errors include local Retry.

### 24.1 Missing or unauthorized Document

Missing and unauthorized resources share one user-facing state:

```text
Not found or no access
```

This avoids leaking resource existence.

The surrounding Workspace/Source shell remains available where possible so navigation can recover.

## 25. Visual design language

Phase 2.5 formally adopts a **Linear/GitHub-inspired Workbench**.

The intent is not visual imitation. The frontend adopts these principles:

- compact
- high information density
- low decoration
- clear hierarchy
- fast scanning
- action-oriented interaction
- restrained color
- consistent panels and separators

## 26. Visual tokens

### Radius

Use small radius:

```text
4px default
6px interactive/floating surfaces
```

Avoid large SaaS-style rounding.

### Shadows

Normal application surfaces do not use shadows. Restrained shadow is reserved for floating surfaces such as Dropdown, Popover, and Dialog.

### Borders

Use subtle 1px neutral borders as the main structural device.

Prefer border/separator/panel boundary/selected background over floating Cards.

### Backgrounds

```text
main content   neutral/white
sidebar        subtle neutral
selected row   subtle accent background
hover          subtle neutral
```

### Accent

Use one restrained accent primarily for selected state, focus, primary action, and active navigation.

### Typography

UI text: approximately **14px**.  
Document body: **15–16px**.

Hierarchy relies on weight, size, spacing, and muted foreground more than decorative color.

### Icons

Use a consistent outline icon language similar to Lucide. Icons support labels rather than replace labels in primary navigation.

### Cards

Cards are intentionally rare. Prefer:

```text
Row
Panel
Section
Separator
```

## 27. Frontend technology

Phase 2.5 keeps a primitive-first approach:

```text
Base UI
+ Tailwind CSS
+ Knowledge Hub semantic components/tokens
```

Do not introduce HeroUI or another opinionated full visual framework.

Shadcn-style component architecture and accessibility patterns may be used as implementation references.

> Base UI owns interaction behavior. Tailwind and Knowledge Hub tokens own appearance.

## 28. Component architecture

Low-level reusable UI primitives belong under `components/ui`.

Product/domain components remain separated by responsibility:

```text
components/
├─ ui/
├─ shell/
│  ├─ app-shell
│  ├─ topbar
│  ├─ workspace-selector
│  └─ primary-nav
├─ knowledge/
│  ├─ knowledge-layout
│  ├─ source-sidebar
│  ├─ source-selector
│  ├─ tree-filter
│  ├─ knowledge-tree
│  ├─ document-header
│  ├─ document-viewer
│  └─ document-inspector
├─ sources/
│  ├─ source-list
│  ├─ source-list-row
│  ├─ source-detail
│  ├─ import-history
│  └─ technical-details
└─ imports/
   ├─ folder-import-form
   ├─ import-summary
   ├─ import-change-group
   ├─ import-warning-summary
   └─ import-sticky-footer
```

Product behavior must not leak into generic UI primitives.

## 29. Frontend state strategy

Phase 2.5 does not introduce Redux, Zustand, or another application-wide state framework.

State ownership:

```text
URL
→ Workspace / Source / Document

Server data
→ Workspace / Source / Tree / Document / Revision / Import state

Local component state
→ Tree expansion
→ Tree filter
→ Inspector open
→ Drawer state
```

A global state library should only be added later if a concrete requirement proves local ownership insufficient.

## 30. Domain contract boundary

Phase 2.5 does not redesign or bypass Phase 0–2 application/domain contracts.

It keeps:

- Workspace identity/access resolution
- KnowledgeSource semantics
- Source ownership
- stable Document identity
- immutable revisions
- archive lifecycle
- Tree behavior
- folder ingestion
- SourceEntry/provenance model
- Preview → Confirm → Apply
- sync-version conflict handling
- authorization rules

Frontend restructuring MUST NOT weaken server-side authorization.

URL parameters are navigation inputs, never authorization proof.

A narrow read-only projection may be added where the approved UI needs information already stored by the existing domain model, e.g. reading existing SyncRun history for Source management. Such a projection MUST NOT alter lifecycle semantics.

## 31. Implementation order

Because the product is not live, implementation is a direct frontend replacement rather than a migration:

```text
1. App Shell + new route hierarchy
2. Knowledge split-pane
3. Markdown renderer + Document Header + Inspector
4. Sources list + Source Detail
5. New Import / Update entry points
6. Full-page Import Preview
7. Remove obsolete frontend pages/components/routes
8. Responsive behavior
9. Loading / Empty / Error states
10. Accessibility + keyboard behavior
11. Linear/GitHub visual polish
12. E2E and regression verification
```

Backend/domain code should change only if an existing contract has an actual defect or a narrowly missing read projection exposed by the frontend implementation.

## 32. Acceptance criteria

Phase 2.5 is complete when all of the following are true.

### Application Shell

- Workspace selector is persistent.
- Primary navigation contains only Knowledge and Sources.
- No placeholder future navigation exists.
- Workspace switching is deterministic.

### Knowledge

- Only one Source Tree is displayed at a time.
- Tree remains visible while changing Documents on desktop.
- Tree expansion state survives Document navigation.
- Tree filter operates locally.
- Archived content is hidden by default.
- Markdown renders safely.
- Document body has readable maximum width.
- Document Inspector provides Details and History.
- Document metadata does not clutter article content.

### Sources

- Source management is removed from the primary Knowledge content area.
- Sources appear in a compact row/list.
- Latest import status is visible from the list when available.
- Source Detail provides overview, import history, and collapsed technical information.
- Update from folder uses one canonical workflow.

### Import

- Preview uses a dedicated page.
- Changes are semantically grouped.
- Unchanged items are collapsed by default.
- Warnings and blockers are visible globally and locally.
- Blockers prevent Apply.
- Stale Preview prevents Apply.
- Apply actions remain accessible through a sticky footer.
- Success returns to Source Detail.
- Failure preserves Preview context.

### Responsive

- Wide desktop supports optional Inspector.
- Medium layout moves Inspector into a Drawer.
- Narrow layout uses full-page Document reading.
- Narrow Tree navigation uses a Browse Drawer.
- Only one overlay Drawer can be open at once.

### Accessibility

- Focus state is visually obvious.
- Tree supports keyboard navigation.
- Dropdown/Dialog/Drawer behavior uses accessible primitives.
- Loading and errors remain understandable without relying only on color.

### Visual quality

- UI follows Linear/GitHub-inspired compact workbench language.
- Structural borders replace excessive Card/shadow usage.
- Radius remains restrained.
- Information density is appropriate for internal knowledge work.
- Reading content remains visually distinct from management UI.

## 33. Definition of Done

Phase 2.5 is not complete merely when the frontend looks more polished.

It is complete when:

> Phase 3 Workspace Governance, Phase 4 Search, Phase 5 Human Authoring, and Phase 6 Publishing can be added without redesigning the application shell, routing strategy, Knowledge Explorer, or Sources management structure.

Roadmap:

```text
Phase 0   Foundation
Phase 1   Knowledge Core
Phase 2   Folder Ingestion
Phase 2.5 Frontend Product Baseline
Phase 3   Workspace Governance
Phase 4   Search
Phase 5   Human Authoring
Phase 6   Publishing
Phase 7+  Agent / Retrieval capabilities
```

Phase 2.5 therefore establishes the long-lived frontend foundation for the remainder of the Knowledge Hub roadmap.

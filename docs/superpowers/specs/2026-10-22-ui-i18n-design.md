# UI i18n (en + zh-TW) — Design

Status: **deferred**. Agreed in brainstorming on 2026-10-22; not scheduled. The only part
shipped so far is the user guide defaulting to zh-TW (see "What already exists").

## Goal

Every string the interface writes — buttons, menus, labels, empty states, toasts, error
messages, `aria-label`/`title`/`placeholder`/`alt`, page metadata — reads in the reader's
language, English or Traditional Chinese. Document content, user-written titles, and
machine-readable fields in MCP/API responses are not translated.

## What already exists

- The UI is English literals in about 200 `.tsx` files under `src/components` and `src/app`;
  `<html lang="en">` is fixed in `src/app/layout.tsx`.
- Two guides are bilingual, one content object per locale (`GuideLocale = "en" | "zh-TW"`
  in `src/components/imports/import-guide-content.ts`), chosen by `?lang=`.
- The user guide (`src/app/w/[workspaceId]/help/page.tsx`) defaults to zh-TW; only
  `?lang=en` shows English. The import guide still defaults to en.
- Dates format with one constant, `UI_LOCALE = "en-US"` (`src/lib/format-date.ts`). The
  design language (§15) names this as waiting on a server-side locale decision; this spec
  is that decision.

## Decisions

| Question | Decision |
|---|---|
| Scope | Whole UI, en + zh-TW |
| Who decides the language | `locale` cookie, else `Accept-Language`, else the fallback locale |
| Mechanism | A small in-repo module; no i18n dependency |
| Translations | Claude drafts; a glossary is agreed first |

The fallback locale is `zh-TW`, one constant in `src/i18n/locales.ts`, matching the user
guide's zh-TW-first choice. In stage 0 the user guide switches to the shared resolver so
the two cannot disagree. That is a deliberate change for the guide: today it ignores the
browser and always defaults to zh-TW, and after stage 0 an English-preferring browser
gets English.

Rejected: next-intl (another dependency on top of the patched Next 15.5.25, a second
middleware to merge with the CSP one, untyped parameters in JSON messages), Lingui
(an SWC plugin and an extraction step, more than two locales need), URL prefixes (every
existing `/w/…` and `/s/:token` link would need a redirect, for SEO an internal tool does
not need), and a per-user DB preference (a migration, and anonymous share readers need
the header fallback anyway).

## Architecture

```text
src/i18n/
  locales.ts          LOCALES, Locale, FALLBACK_LOCALE; pure parse + negotiate
  messages/en.ts      source of truth, `as const`, grouped by area { shell, knowledge, … }
  messages/zh-TW.ts   `const zhTW: Messages = {…}` — a missing or extra key fails typecheck
  server.ts           getLocale(), getMessages(); reads cookies()/headers()
  client.tsx          <LocaleProvider locale>, useMessages(), useLocale()
```

**Resolution.** The `locale` cookie, if its value is in `LOCALES`; else `Accept-Language`
by q-value, where `zh`, `zh-Hant`, `zh-TW`, `zh-HK`, `zh-MO`, `zh-CN` and `zh-Hans` all
map to `zh-TW`; else `FALLBACK_LOCALE`. No middleware change: the root layout already
calls `headers()`, so pages are already dynamic. Anonymous `/s/:token` uses the same rule.

**Client components.** The provider passes only the locale string. Both dictionaries are
imported statically and the client picks one: downloaded once and cached, rather than
re-sent in every RSC payload. Measure the two gzipped dictionaries in stage 0; split per
locale only if they exceed about 30 KB.

**Switching.** A choice in the user menu writes the cookie (`path=/`, `SameSite=Lax`,
one year) and calls `router.refresh()`. The cookie is not sensitive and is not httpOnly;
the server re-validates it against `LOCALES`, so a forged value yields the fallback.

**Changed alongside:** `<html lang={locale}>`; `format-date.ts` takes the locale as a
parameter instead of `UI_LOCALE` (the UTC-first-pass-then-zone behaviour is unchanged);
both guides default `?lang` from `getLocale()`.

## Error messages

Domain errors and API responses stay English with a stable `code`
(`{ error: { code, message, details } }`). Modules may not import `next` and cannot know
the reader, and MCP/API callers want the code. The UI translates: `messages.errors[code]`,
falling back to the server's English `message`, so a new code degrades to English, never
to a broken string. Parameters come from `details`, never from parsing `message`.

Codes are strings, so the type system cannot force completeness. A unit test scans
`src/modules/**` for codes (`super("CODE", …)`, `code = "…"`) and requires an entry in
both dictionaries for every user-visible one; codes never shown to users are listed in
the test as explicit exclusions.

## String rules

These rules also go into `frontend-design-language.md`.

1. Keys name the place, not the English: `knowledge.toolbar.save`, not `"Save"`.
2. Interpolation is a function: `movedTo: (folder: string) => \`Moved to ${folder}\``.
3. Plurals are written in that function (`n === 1 ? … : …`); zh-TW has none. No plural helper.
4. A sentence with a link or emphasis is one key taking the parts as parameters —
   `(link: ReactNode) => <>Open {link} to…</>`. Never concatenate keys: Chinese word order differs.
5. `aria-label`, `title`, `placeholder`, `alt`, and `<title>`/metadata are translated.
6. Dates and numbers go through `Intl` with the current locale.

**Regression guard.** `react/jsx-no-literals` (already installed via
`eslint-plugin-react`), enabled per directory as each stage lands.

## Glossary

The first deliverable, reviewed before any other string is translated. It decides, term
by term, whether to translate or keep English (Workspace, Source, Hub, My Space,
Revision, Share link, Discussion, Archive, …). The existing zh-TW guides translate
folder, import, sync, preview, apply, and archive, but keep Hub, My Space, and Source in
English, and say button names match the English interface. Once the UI is translated
that sentence is no longer true, so the guides are rewritten to the glossary in the stage
that translates the controls they name.

## Stages

Each stage is one PR and can merge alone; untranslated areas stay English.

0. Mechanism: `src/i18n/`, resolution, provider, language switch, `lang`, `format-date`,
   the error-code table and its test, and the glossary.
1. `shell`, `ui`, `errors`, not-found, global-error: seen on every page.
2. `knowledge`: reader, editor, discussions, sharing. The largest; may split.
3. `sources` and `imports`, including the import guide's default.
4. `workspaces`, `personal`, `search`, `help`.

Each stage extracts strings, writes zh-TW, adds its directories to `jsx-no-literals`, adds
the error codes its area shows, and attaches zh-TW screenshots.

## Testing

| Requirement | Test |
|---|---|
| Both dictionaries have the same keys | `make typecheck` |
| Resolution: cookie > Accept-Language > fallback; bad cookie ignored; zh variants → zh-TW; q-value order; empty or garbage header | unit test on `locales.ts` |
| Every user-visible error code has both translations; unknown codes fall back to English | unit test scanning `src/modules` |
| Switching makes the page zh-TW, sets `<html lang>`, survives reload | e2e |
| Anonymous `/s/:token` follows Accept-Language | e2e |
| zh-TW dates; SSR and hydration agree | `format-date` unit tests, extended |
| Existing e2e unaffected | Playwright's default `Accept-Language: en-US` resolves to en; stage 0 verifies this and pins `locale: "en-US"` in `playwright.config.ts` so it does not depend on the default |

## Risks

- Chinese strings differ in length: buttons and narrow columns may wrap or truncate.
  Mitigation: zh-TW screenshots on every stage.
- Both dictionaries ship in the client bundle; measured in stage 0.
